AI control contracts and operations

Gap addressed: "AI control contracts and operations" in the reference TODO (17 classes: contracts plus operation/team/definition classes). Companion to AI behavior trees: trees decide, contracts and operations carry out.

Verified (static from Linux symbols and decompile; in-game test pending, see end)

  • Classes (GameCore::AI::, names and sizes from DWARF):
  • Control::Contract base (109 functions) with five subtypes, each with Initialize / Execute / Update / Validate / Read / Write: UnitRequestContract (29 functions, ~10.7 KB, also UnitCreated/BuildingCreated/DistrictCreated), TechResearchContract, CivicResearchContract, PurchasePlotContract, DiplomaticActionContract. Plumbing: Control::Factory (CreateContract, DestroyContract), Control::Handle, Control::Instance, Control::Manager (33 functions: DoTurn, CreateController, OnUnitCreated, ...), Control::UnitEvaluator (IsDoneRecruiting).
  • Operation::Operation (102 functions), OperationTeam (61), OperationDef, TeamDefinition, TeamRequirement, OperationTarget, OperationEvaluator (24: GetNextPotentialTarget, GetOdds, Value, GetRally), OperationConditionFunctions, OperationsListReader.
  • Link to trees (from AI behavior trees): tree nodes carry a Contract ID (Build Unit, Add Goal Tech, Recruit Units, Cancel Contract, ...). A tree asks for something by creating a contract; the Control side fulfils it. Operations run a tree each: AiOperationDefs.BehaviorTree.
  • Operation data (live DB, 16 defs in the base game): AiOperationDefs (target type, enemy type, behavior tree, priority, distances, MinOddsOfSuccess, SelfStart, MustBeAtWar, MustHaveNukes, OperationType, TargetLuaScript, ActiveEmergency), AiTeams, AiOperationTeams (team -> operation, min/max units, strength advantages, SafeRallyPoint, Condition), OpTeamRequirements (team, AI unit type, min/max number/percentage), AiOperationTypes (7 values), AiOperationLimits (empty in base), AiOperationLists + AllowedOperations (which operations a leader list may run; Default_List has 12).
  • Script-supplied targets. An operation with TargetType = TARGET_SCRIPT_SUPPLIED gets its target from Lua: OperationEvaluator::GetNextPotentialTarget (old RVA 0x4e3e80) calls Lua::Utility::CallProcessor with the operation's TargetLuaScript string, i.e. GameEvents.<TargetLuaScript>. It reads PlotX and PlotY from the result table (hashes 0x1d5666bb / 0x6a51562d = ~crc32 of the names, verified) and also touches Extra (0x7301dd9e). Only one target is offered per evaluation (it returns false on the second call). The Civ Royale DLC uses this (CivRoyale_GetSafeZone, DLC/CivRoyaleScenario/Data/CivRoyaleScenario_AI.xml), and its Lua handler writes targetInfo.PlotX/PlotY.
  • Team conditions. AiOperationTeams.Condition is a name hashed and looked up in a table of C++ functions (OperationConditionFunctions::MeetsCondition, old RVA 0x4dcd10); an unknown name is false. The base game registers only IsCoastalTarget (the functions list has Initialize/IsCoastalTarget/Uninitialize), so conditions are not extensible from data.
  • Observation logs (Logs/): AI_Operation.csv (turn, player, operation, notes, team status), AI_Operation_Eval.csv (turn, player, enemy, operation, value: the score each candidate operation gets), AI_Planning.csv, AI_Behavior_Trees.csv.

Inferred (not tested)

  • Contracts are created by tree nodes and by the Control manager and run per turn by Control::Manager::DoTurn; the contract lifetime (create, estimate/present value, execute, fail/cancel) matches the Contract method names but is not traced.
  • An operation added through the five tables plus a Default_List entry becomes available to every default AI; whether it is actually started depends on its evaluation value and available units.

For modders

  • A new operation needs: an AiOperationDefs row (use BehaviorTree of an existing tree), an AiTeams row, an AiOperationTeams row, OpTeamRequirements rows, and an AllowedOperations row in the list a leader uses (Default_List).
  • To control where it goes, set TargetType = TARGET_SCRIPT_SUPPLIED and TargetLuaScript = <Name>; register GameEvents.<Name>.Add(fn); fn(targetInfo) sets targetInfo.PlotX, targetInfo.PlotY.

First in-game result (2026-10-30, mod BTOpTest, turn 1)

  • Verified in game: the mod's operation reaches the AI. On turn 1 the evaluator called GameEvents.BTTest_GetTarget once (empty argument table; handler returned the map centre 37,23) and AI_Operation_Eval.csv lists "BTTest Operation" with value 0.0 for player 0.
  • Turn 12 result: the target script was called 166 times (about 14 per turn, one per AI player per turn, from GetNextPotentialTarget; always the same answer 37,23). AI_Operation_Eval.csv shows value 0.0 for every player every turn. Because SelfStart is true, AI_Operation.csv shows "BTTest Operation: Started" followed in the same turn by "Operation complete" for each of the 14 AI players, every turn (154 start/complete pairs). No team lines, no "running TARGET" line (compare "Settle New City running, TARGET 19:8"). The human player 0 is evaluated but not started.
  • Why it completes at once (static, from decompile, plus the tree log): Operation::IsFinished (old RVA 0x4db9c0) has cases for four target types only: TARGET_BARBARIAN_CAMP (finished when the camp is no longer known), TARGET_ENEMY_COMBAT_DISTRICT / TARGET_ENEMY_PASSIVE_DISTRICT (finished when the target plot is no longer a known enemy district), TARGET_MY_CITY and TARGET_SETTLE_LOCATION (never finished). Every other type, including TARGET_SCRIPT_SUPPLIED, falls through to return true. IsTargetValid (0x4dbcd0), on the other hand, accepts TARGET_SCRIPT_SUPPLIED. The tree nodes that call IsFinished are OperationAttackUnits, OperationAttackTarget ("Operation Attack"), OperationAttackCityNode, OperationPillageCityNode, OperationSiegeCityNode, OperationAirstrikeCityNode, CanAlphaStrikeCityNode and IsCityThreatenedNode. OperationAttackUnits::Update (0x56d880) returns state 1 immediately when the operation is finished. The reused tree "Simple Operation Attack" contains "Operation Attack Units" (nodes 2, 9, 16, 20) and "Operation Attack" (21), and AI_Behavior_Trees.csv shows its first run as "Operation Attack Units: SUCCESS" with the root Concurrent ending in FAILURE (Decode Trigger: Value 0), after which the operation is logged complete. Verdict: the tree finishes at once because it asks IsFinished, which is always true for a script-supplied target. Whether a team never formed as well was not checked.
  • Consequence for modders: a script-supplied-target operation must use a tree without the IsFinished nodes (Civ Royale's tree mostly uses Operation Move, Operation Defend Units, Operation Change Target, Recruit Units, plus its own Lua condition), or use another target type.
  • So a mod-added operation is created and run by the engine every turn and its Lua target hook fires; making it do something needs a team of units and a tree that keeps running.

Run 2 (2026-10-30, own tree "BTTest Op Tree" without IsFinished nodes, turn 12)

  • The operation now does real work for all 14 AIs each turn (AI_Operation.csv 154 starts): "Recruiting minimums: UNIT_WARRIOR", then "Operation Recruit: Recruited 1, Contract for: UNIT_..." (a UnitRequestContract created by the Recruit Units node; the node logs "Recruited: 1 ... Ready: YES"). 25 times "No recruits to reach minimum".
  • The Lua target is used: Operation Move logs "Moving to rally position 37: 23" (the script's PlotX/PlotY), and AI_Operation.csv shows "BTTest Operation running, TARGET 37:23" 4 times. So a script-supplied target becomes the operation's target/rally point.
  • The operation still ends most turns: Operation Move returned FAILURE 146 times (root Concurrent FAILURE, then "Operation complete") and RUNNING only 12 times. Why the move fails was not examined (untested guesses: the map-centre plot is water or unreachable, or the team is not formed yet).
  • Verified: with a tree free of IsFinished nodes the operation goes through recruit, contract and move; the earlier immediate completion was caused by the reused tree, as decompiled.

Open / next

  • Why Operation Move fails (plot type/reachability of the script target, team readiness); pick a land target near the capital and see whether the operation stays running and a team forms.
  • Contract classes: lifecycle and which tree nodes create which contract type.

Look for BTOPTEST: lines in Lua.log and for "BTTest Operation" in AI_Operation.csv, AI_Operation_Eval.csv and AI_Behavior_Trees.csv. Scripts/BTOpTest.lua

-- BT Operation Test: proves an operation's TargetLuaScript is called as GameEvents.<name> and its PlotX/PlotY become the target
print("BTOPTEST: script loaded");
local calls = 0;

function BTTest_GetTarget(targetInfo)
    calls = calls + 1;
    local keys = {};
    if type(targetInfo) == "table" then
        for k, v in pairs(targetInfo) do table.insert(keys, tostring(k) .. "=" .. tostring(v)); end
    end
    local w, h = Map.GetGridSize();
    local x, y = math.floor(w / 2), math.floor(h / 2);
    print("BTOPTEST: target script called #" .. calls .. " fields={" .. table.concat(keys, ",") .. "} turn=" .. tostring(Game.GetCurrentGameTurn()) .. " returning " .. x .. "," .. y);
    if type(targetInfo) == "table" then targetInfo.PlotX = x; targetInfo.PlotY = y; targetInfo.Extra = 1; end
    return true;
end

local treeCalls = 0;
function BTTest_OpTreeCond(targetInfo)
    treeCalls = treeCalls + 1;
    if treeCalls <= 40 then print("BTOPTEST: op tree condition #" .. treeCalls .. " turn=" .. tostring(Game.GetCurrentGameTurn())); end
    if type(targetInfo) == "table" then targetInfo.Extra = 1; end
    return true;
end

GameEvents.BTTest_GetTarget.Add(BTTest_GetTarget);
GameEvents.BTTest_OpTreeCond.Add(BTTest_OpTreeCond);
print("BTOPTEST: handler registered");
