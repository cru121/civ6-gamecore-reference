Notes (★)

City::Buildings::AddGreatWork

Places a great work into the first empty slot in the city that accepts its object type.

  • Looks up the great work's definition and object type, then scans the city's buildings and slots (empty slot = index field 0xFFFFFFFF). [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Uses Game::Culture::IsValidObjectForSlot(slotType, objectType) to decide whether a slot accepts it, writes the index into the first valid slot, then checks IsBuildingThemedCorrectly and, if themed, dispatches a signal. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Returns nothing. If no slot fits, it silently does nothing. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • The themed-building signal probably drives game effects for theming bonuses. (Low-medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • The 'add' half of moving a great work. Because it returns nothing, a caller must check CanAddGreatWork first if it needs to know whether it will work. [inferred; evidence: static-analysis — decompilation read in Ghidra]

City::Buildings::AddGreatWorkToSlot

Places a great work into a specific building's slot. A negative slot means 'first empty slot in that building'.

  • Finds the entry for the given building type, resolves a negative slot to the first empty one, bounds-checks, writes the index at slot+4, then calls CheckForThemedBuilding. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Does not check slot-type compatibility itself (unlike AddGreatWork). [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Callers (relic, artifact, hero-epic and random-product code) probably validate compatibility beforehand. (Medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • The precise-placement variant. A wrapper exposing it would need to enforce slot-type checks itself. [inferred; evidence: static-analysis — decompilation read in Ghidra]

City::Buildings::IsInCity

True if a great work with this index sits in any slot of any building in this city.

  • Same walk as RemoveGreatWork, returning true on the first slot whose index matches. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • none [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Useful to find which city currently holds a great work. The game-wide owner field is not updated on trades (see SetGreatWorkPlayer), so this is the reliable 'current holder' test. [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • On a real save, IsInCity returned true for a work held by a leftover Palace slot entry in a city that no longer has the Palace (a "ghost slot"), while the building-based UI lists did not show it; the trade screen did show it. [verified; evidence: runtime — Observed in-game (real save, 2026-10-01)]

City::Buildings::RemoveGreatWork

Clears the slot that holds a given great work in a city. Returns the slot number it was in, or -1 if this city does not hold it.

  • Walks the city's building entries (array at this+0xc8, count at this+0xd8, 0x20 bytes each) and each building's slots (pointer at entry+0x8, count at entry+0x18, 8 bytes each). The great work index is at slot+4. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • On the first match it writes 0xFFFFFFFF into that slot and returns the slot number within its building. It does not report which building it was in, and stops after the first match. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • It does no tourism/yield recalculation, sends no event or signal, and does not touch the game-wide great work list. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Callers always obtain the city's Buildings through FAutoVariable::edit(city+0xca0) first. This looks like change tracking (save / multiplayer sync), so calling RemoveGreatWork on an un-edited object may skip that tracking. (Medium: mechanism read from the accessor, purpose inferred.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Tourism and yields appear to be computed on demand by getters (e.g. GetYieldFromGreatWorks), so nothing else needs refreshing after removal. (Medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • This is the missing 'take a great work out of a city' operation. No gameplay-side Lua method can currently do it. [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • On its own it leaves the work in no city. The game pairs it with a placement call (ReceiveGreatWork) and retries if placement fails. [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • See the topic note great-works-moving.md. [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Called through the edit() accessor (command remove), a work leaves its slot but stays in the game-wide record list ("limbo"): the per-city getters then count no yield and no tourism for it, and Game.GetGreatWorkPlayer / HasGreatWorkBeenCreated still know it. [verified; evidence: runtime — Observed in-game (2026-09-29 to 2026-10-03, single player, Frida live channel)]
  • Archive swap: after removing the Palace work and placing a different work into the freed Palace slot, a save/reload showed the new work with its yields in the Palace. [verified; evidence: runtime — Observed in-game (2026-09-29 to 2026-10-03, single player, Frida live channel)]
  • Removing the whole Palace (City::Buildings::RemoveBuilding via edit()) while its slot held a work: the game did not refuse and did not crash; the building and its slots disappeared and the work went to limbo with its record intact (2026-10-03). The ghost scan found no leftover slot entries afterwards. [verified; evidence: runtime — Observed in-game (2026-09-29 to 2026-10-03, single player, Frida live channel)]
