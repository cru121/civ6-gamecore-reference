Notes (★)

Game::Culture::AddRelic

Chooses a relic, creates its game-wide record, places it in a slot, and announces it. Its only caller is Player::Religion::CreateRelic.

  • Selection among the pool is random (weighted). (Medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Because AddGreatWorkToSlot silently does nothing for an unknown building entry or an out-of-range slot (see its note), calling AddRelic with a valid city, a relic-holding building type and an out-of-range slot should create the record and skip placement. The notification would still say the relic was placed. Untested. (Low-medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Called with a valid city, a relic-holder building type and an out-of-range slot, AddRelic creates the record and notifies, but places the relic in no slot (it ends in limbo). This is what the archive hook relies on; verified with the hut xN test command and reload. [verified; evidence: runtime — Observed in-game (2026-09-30, single player)]

Game::Culture::FindOrAddGreatWork

Returns the position (list index) of the game-wide record for a great work type, creating the record if none exists.

  • Scans the game-wide list (begin at Culture+0x118, end at +0x120, 0x18 bytes per record) for a record whose first field equals type; if found, returns its position. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Otherwise appends a new record through the tracked accessor (edit() on the list at Culture+0x108) and returns the new position. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Record layout (0x18 bytes): +0x00 great work type (u32); +0x04 player (s32, initialised to -1); +0x08 the game's current turn at creation (read from the game instance at +0xc0); +0x10 a text string, initialised empty. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • The type is an index into the great work definition collection (Definitions::GetGreatWorkDefinitions). [verified; evidence: static-analysis — decompilation read in Ghidra]
  • The "Created in " text comes from the record's creation-turn field (fits the observation: two works created one turn apart differ by 50 years). (Medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • The "Created by" text comes from the string at +0x10, which normal creation code (great people, relics, artifacts) probably fills in; works spawned only with this function have it empty. (Medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • The player field (+0x04) starts at -1 and is set by SetGreatWorkPlayer; see that note. (Medium.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • An archive that only remembers a work's type would lose its creation turn, creator text and player. To restore a work faithfully, keep the whole record, or leave the record in the game-wide list and only move the slot (what the experiments did). [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Creating a work with this function alone is enough to make it exist in limbo, but it will lack the creator text. [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Called through the Frida tool for works 0 and 1: created records at list indexes 0 and 1; a second call with an existing type returned the existing index and added nothing. [verified; evidence: runtime — Observed in-game (2026-09-29/30)]
  • A tooltip for a work created this way reads "Created in 950 BC" (the other, created a turn earlier, 1000 BC) and shows an empty "Created by". [verified; evidence: runtime — Observed in-game (2026-09-29/30)]

Game::Culture::SetGreatWorkPlayer

Writes a player id into the game-wide great work record.

  • Calls edit() on the tracked list at Culture+0x108, then writes the player at record[index0x18 + 4]. [verified; evidence: static-analysis — decompilation read in Ghidra]*
  • The player field is initialised to -1 when the record is created (), so this call is what fills it in. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • Not called in the trade path (Enact, PostEnact, City::Manager::Transfer). Called from GrantRandomProduct, CreateHeroEpicGreatWork and Player::Operations::Manager::Process. [verified; evidence: static-analysis — decompilation read in Ghidra]
  • That field is probably the creator of the work, not its current holder; Game.GetGreatWorkPlayer most likely returns the creator and does not change on trade. (Medium; inferred from callers only.) [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • Do not read this as 'who owns it now'. Use IsInCity across the player's cities for the current holder. [inferred; evidence: static-analysis — decompilation read in Ghidra]
  • On a real save from a forum report, the record "player" field of works held by other civilizations was the creator, not the holder; the field is also used for theming, so overwriting it with the holder is not safe. [verified; evidence: runtime — Observed in-game (real save, 2026-10-01)]
