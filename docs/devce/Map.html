AddPlotYield

Arguments: iPlotIndex — plot index; eYield — yield type; iAmount — amount to add; event only for >0

Writes - per-plot yield entry in variant map at this+0xb0 (creates entry if absent, adds amount to the yield slot)

Side effects - Reporting::Event::Send hash 0x45b517d6 with plot, city and localized text, only when amount>0 and plot visible

Input checks: Invalid plot or amount<1 skips the event but still performs the stored add (amount added even if negative); out-of-range plot index goes to a scratch entry; out-of-range yield adds to a fallback field.

Preconditions - game thread - valid plot index recommended

Multiplayer: may-desync: event depends on local observer visibility but state change is deterministic. Risk: medium (stored yield change plus local-only UI event). Confidence of the reading: medium.

Verified from the code - uses virtual map GetPlot at vtable+0x60 - message only when amount >= 1 and local visibility value > 0 - bounds checks for index and yield; fallback writes elsewhere - switch on yield 0-5 selects text, all cases fall to same code in decompile

Inferred - the +0xb0 map is plot index to yield list - the sent event is the plot yield popup

Open questions - what the fallback fields at +0x18/+0x30 of the scratch entry represent

ChangeNaturalWonderCount

Input checks: None; no clamp, negative results allowed.

Preconditions - map instance exists

Verified from the code - computes current plus delta and stores through a move-assign helper

SetRevealedImprovementType

Arguments: ePlayer — player whose knowledge is changed; 1000 selects the global/default visibility record; iPlotIndex — plot index; eNewValue — improvement type to record

Writes - 16-bit revealed improvement entry for the plot in the player's visibility data (via auto variable at visibility+0x150)

Input checks: Plot index and player id are not range checked (unchecked array indexing, crash risk). Returns false when the layer index is out of range, the layer is null, or the value is unchanged.

Preconditions - valid player id or 1000 - valid plot index - game thread

Multiplayer: may-desync: per-player visibility state; keep it consistent on all clients. Risk: medium (Unchecked indexes; changes what a player sees for a plot.). Confidence of the reading: medium.

Verified from the code - Player id 1000 uses the record at this+0x50, otherwise looks up via the mapping tables - Layer index from this+0x18 is bounds-checked against count at record+0x240 - Writes a short only if different, returning true - Returns false otherwise

Inferred - Field at this+0x18 is the improvement layer slot; this+0x1c is the resource layer slot in the sibling function - 1000 is the 'observer/all' pseudo player

Open questions - Whether callers must also refresh the UI

Preconditions - valid player id or 1000 - valid plot index - game thread

Verified from the code - Identical structure to SetRevealedImprovementType but layer index from this+0x1c - Writes a short and returns true only if the value differs

SetRevealedRouteType

Arguments: ePlayer — player whose visibility record is edited; 1000 selects a special alternate record (observer/global); iPlotIndex — plot index into the per-layer revealed route array; eNewType — route type to store as the revealed route

Writes - revealed route type (16-bit) for the plot in the player's visibility data, inside a VariantMap edited via edit()

Side effects - marks the player's visibility variant map as edited (change tracking via edit())

Input checks: Player id 1000 uses a fallback record; any other id indexes the player table without a visible range check (crash risk on bad id). Layer index is checked against a count; the plot index is NOT bounds checked (crash risk). Failed layer check returns false silently.

Preconditions - valid player id (or 1000) - valid plot index - visibility manager initialized

Multiplayer: may-desync: visibility state mutation; only safe if run identically on all clients. Risk: medium (unchecked plot index and player index; visibility data only, so wrong values are cosmetic but bad indices can crash). Confidence of the reading: medium.

Verified from the code - returns false when the layer index is not below the record's count - stores the value as a 16-bit short only if different from the current one - player 1000 takes a different record path

Inferred - player 1000 is the 'no player/observer' slot - this+0x20 is the current visibility layer or team index

Open questions - exact meaning of this+0x20 - whether edit() affects replication or only dirty-flagging

SetVolcanoActive

Arguments: bMustBeNamed — only consider volcanoes that have a name

Writes - chosen volcano record's 'active since turn' field (+0x14) set to current turn - uses and advances the game random state (Choose Active Volcano Roll)

Side effects - Random::Get roll consuming random state - Reporting::Event::Send with plot, flag and visibility - Reporting::Notification::Send to each player that can see the plot with localized text - Only runs when more volcanoes are inactive than active

Input checks: Silent return when no inactive volcano candidate exists (count difference must be positive). Notification only for players with the plot visible.

Preconditions - gameplay state - map with volcano features - game thread

Multiplayer: may-desync: uses the shared random generator and emits UI notifications; must run identically on all clients. Risk: high (Consumes random state and sends notifications; call order matters for sync.). Confidence of the reading: medium.

Verified from the code - Rolls Random::Get with label 'Choose Active Volcano Roll' - Iterates volcano list and skips those already active, and unnamed ones when bMustBeNamed is true - Sets a turn field on the selected entry and sends a reporting event and per-player notification - Notification only if the player's visibility array has the plot revealed

Inferred - Entry field +0x14 is the activation turn; -1 means inactive - Vtable calls give total/active volcano counts

Open questions - Meaning of virtual calls at +0x58/+0x68 - Notification type hash identification

SetVolcanoInactive

Side effects - Random::Get roll - Reporting::Event::Send - Reporting::Notification::Send to players who see the plot, different notification type than the active variant

Input checks: Silent return when no active volcano exists. Skips unnamed volcanoes if bMustBeNamed.

Preconditions - gameplay state - game thread

Multiplayer: may-desync: consumes shared random state and sends notifications. Risk: high (Random roll plus notifications; ordering matters.). Confidence of the reading: medium.

Verified from the code - Rolls Random::Get with label 'Choose Inactive Volcano Roll' - Picks among active entries and writes -1 into the entry at +0x14 - Sends reporting event and notification to each player with visibility

Inferred - Mirror of SetVolcanoActive

Open questions - Same unknown virtual calls as the active variant
