SetAtWar

Arguments: a — first player id; b — second player id; war — war type; -1 = peace

Writes - war-state/turn pair for the player pair in a triangular matrix at this+0x188 - aggressor and turn pair for the player pair in matrix at this+0x1b0 (aggressor = a, or -1 on peace) - current game turn stamp copied from game object +0xc0

Side effects - if players differ, pair not yet met and war type != -1: Player::Manager::Meet is called (first meeting) - LogDiplomaticEvent with At War (war type string) or Peace - on war: ResetDenouncement on both players, ExpelFromTerritory(reason 3) both ways, AddOutgoingVisibilityBlocker three times - on peace: ExpelFromTerritory(reason 4) both ways and RemoveOutgoingVisibilityBlocker three times

Input checks: no bounds check on player ids (unchecked triangular index); when a==b the first meet branch is skipped but state write still happens at a degenerate index; war-type not validated

Preconditions - both ids valid active players - gameplay Lua state, game thread

Multiplayer: may-desync: mutates global diplomatic state; must be executed identically on all clients. Risk: high (unchecked player index, changes global diplomacy, visibility and unit placement). Confidence of the reading: medium.

Verified from the code - war type 0xffffffff selects the Peace branch - tri-matrix index uses player count at +0xb8 - edit() called on two FAutoVariable maps - Meet called only when pair not already met and war type != -1 - expel and visibility-blocker calls happen only if both players' flag at +600 is non-zero

Inferred - flag at +600 likely means player is alive/major - maps at +0x188 and +0x1b0 hold war state and aggressor - the +0xd0 per-pair byte is a has-met flag - war-type string is used purely for logging

Open questions - exact meaning of ExpelFromTerritory reason codes 3 and 4 - why visibility blocker is added twice for the same ordered pair

SetIsInDefensivePact

Arguments: a — first player; b — second player; pact — true to create, false to end

Writes - pair entry in triangular-indexed array at this+0x138: flag byte and turn (from game +0xc0)

Side effects - signal dispatch (Unit, Plot) pact-start (+0xd98) or pact-end (+0xdb0) with the two players' player objects as args - LogDiplomaticEvent 'Defensive Pact' or 'Defensive Pact Ends'

Input checks: No range or equality checks on ids; unchecked pair index and player-array lookups (crash risk).

Preconditions - game thread - two valid distinct player ids

Multiplayer: may-desync: diplomatic state. Risk: medium (unvalidated indices). Confidence of the reading: medium.

Verified from the code - symmetric pair index computed from min/max of ids - logs strings Defensive Pact / Defensive Pact Ends - different signals for set vs clear

Inferred - signal arg types shown in template (Unit, Plot) are probably Ghidra mislabels of player objects

Open questions - real signal parameter types

SetJointWarTarget

Arguments: initiator — player starting the joint war; partner — allied partner; target — player the war is declared on

Writes - pair table entry at this+0x1d8: target player and current turn

Input checks: No bounds check on ids; triangular pair index is unchecked (out-of-bounds risk).

Preconditions - valid player ids - game thread

Multiplayer: safe-deterministic. Risk: medium (Unchecked pair index.). Confidence of the reading: high.

Verified from the code - Pair index is symmetric so initiator/partner order does not matter for storage - Stores target in the first field and the current turn in the second - Does not declare war itself

Inferred - Passing -1 as target probably clears it

Open questions - Whether callers use the stored turn for expiry

SetSharesSuzerain

Arguments: a — first player; b — second player; c — true if they now share a suzerain

Writes - pair table entry at this+0x228: bool flag and current turn

Side effects - calls LogDiplomaticEvent with text 'Shares Suzerain' or 'No longer shares Suzerain' and an empty second string

Input checks: No bounds checks on player ids (unchecked triangular index). The log is written even if the value did not change.

Preconditions - valid player ids - game thread

Multiplayer: safe-deterministic. Risk: medium (Unchecked pair index.). Confidence of the reading: high.

Verified from the code - Writes bool and turn into pair record - Builds strings and calls LogDiplomaticEvent(this, a, b, text, empty) - Text depends on the bool

Inferred - Used by relationship (diplomatic visibility/modifier) scoring

Open questions - Whether the log appears in UI or only the diplomatic log
