# Player::Religion::CreateRelic

`void __thiscall CreateRelic(Religion* this, PlotCoord plot, RelicSource source)`

Creates a relic near a plot and places it in the nearest relic slot.

## Verified from the decompilation
- Calls GetNearestRelicSlot for the plot (returns a city plus building type and slot), then Game::Culture::AddRelic. If that returns a valid great work, it looks up the slot's work and sends a Reporting event (hash 0x1a71e9f0).

- **If `GetNearestRelicSlot` finds no free relic slot, the function does nothing at all**: no relic is chosen, no record is created, no event is sent. (The relic is chosen inside `AddRelic`, which is only called when a slot exists.) This is the "relic lost when slots are full" behavior.
- Direct callers (13): the combat resolvers (`ResolveMeleeUnitVsUnitCombat` and siblings, `AttackInto`), `Map::Player::Visibility::Manager::ViewPlotContents`, `Unit::Commands::SpreadDissent::Start`, and `GameEffects::Effects::GrantRelic::Apply` (a modifier effect). All relic sources funnel through this one function. Which caller is the goody hut, apostle death or city-state perk is inferred from the names, not verified.

## Observed in-game (2026-09-30, single player)
- With the stock DLL and every relic slot full, calling CreateRelic left the game-wide great work record count unchanged: the relic is never created (it stays in the pool), it is not created and thrown away.
- A hook that, for a human player with no free relic slot, calls AddRelic with an out-of-range slot instead creates the record and archives the relic: confirmed with the `hut xN` test command (the Palace holds one relic slot; relics were archived only once it was full).

## Inferred (not confirmed in-game)
- Any notification or era score a player sees when the slots are full is produced by the caller or another system, not by this function or `AddRelic` (which only announce on success). (Medium; not traced.)
- Relics use the same slot machinery as other great works (AddRelic reaches AddGreatWorkToSlot). (Medium.)
