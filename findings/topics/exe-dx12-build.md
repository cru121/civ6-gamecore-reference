# CivilizationVI_DX12.exe compared with CivilizationVI.exe (DX11)

Same build date (28 Jul 2024), same image base, same section layout. Not published. Short address list: findings/tables/exe_dx12_key_addresses.tsv; full function match: findings/data/exe_dx12_match.tsv. Tools: `tools/exe/dx12_match.py`, `tools/exe/dx12_classify.py`; data in `linux_depot/out/dx12/`.

## Verified (read from the two files)
- `.text` is 0xf94e2c (DX11) vs 0xfa3fcc (DX12) bytes, +61 KB (0.4%). Imports: `d3d11.dll` replaced by `d3d12.dll`; 890 vs 894 imports (DX12 adds `InitializeCriticalSectionAndSpinCount`, `VariantInit`).
- Ghidra finds 54,524 functions (DX11) and 54,817 (DX12).
- Matching by masked bytes (address-dependent operands wildcarded) plus call-graph alignment pairs 53,663 functions (98.4%): 31,925 exact, 16,917 exact among identical copies (paired by order), 4,561 callee-of-matched, 260 fuzzy.
- Unmatched: 861 DX11-only (132 KB), 1,154 DX12-only (200 KB). "Only" means no counterpart was found, so it includes functions that were changed, not only new ones.
- 6,443 of the 6,506 functions of the existing function map (the ones with a Windows address) carry across to the DX12 exe.
- The DX12-only functions that reference graphics imports: `CreateDXGIFactory1`, `D3D12SerializeRootSignature`, `d3d12` ordinals 101 and 102 (import thunks, 6 bytes each). The DX11-only ones: `D3D11CreateDevice`, `CreateDXGIFactory1`.
- The DX12 console help function (8,800 bytes, DX11: 8,009) differs by 4 strings, all DX12-only: `rendermode`, `objectvrs`, `imagevrs`, `multires`.

## Classes of the 1,154 DX12-only functions
Thunks 377, render by string or by neighbouring block 311 (62 + 249), neighbour of a mapped function (ForgeUI 88, Platform 26, library 23, WorldView 4 ...) 185, unclassified 253, other 28.
The renderer code sits in one region (RVA 0x93f000-0x971000): `Renderer::Present`, device and adapter enumeration (`CacheAllDeviceInfo`, `CreateD3DDevice` with D3D12CreateDevice, a "Tier 2 Resource Binding" requirement check), PSO creation and compilation, root signature serialisation, the descriptor heaps ("Generic Descriptor Heap", "Per Frame Descriptor Heap"), command list allocation, `ResidencyManager` and D3D12Residency, mip generation (`MipGenPSO`), the readback path, swap chain destruction and a breadcrumb buffer (GPU crash markers). Source paths in the strings are under `CivTech\Libs\Graphics` and `CivTech\Libs\Platform`. The `Renderer.log` file name is the same as in the DX11 build.

## Inferred
- The variable rate shading reading of `objectvrs` / `imagevrs` / `multires` is from the names only; the commands were not run.
- The 88 ForgeUI-neighbour functions are probably changed (not new) functions whose counterpart did not match; not checked one by one.
- Name transfer for the "exact among identical copies" matches (thunks and similar) can land on a different copy of identical code.

## The 63 mapped functions without a counterpart, decompiled (tools/exe/dx12_pairs.py, dx12_pairdiff.py; decomp11.txt, decomp12.txt, pairdiff.txt in linux_depot/out/dx12/)
Verified (decompiled text of both exes compared after normalising addresses and variable names):
- 21 of the 63 (20 export, 1 low) are not functions in the DX11 Ghidra program at all (mapped address without a function boundary), so they were never real differences.
- 42 are functions; 29 have a DX12-only candidate between the same matched neighbours, 13 have none.
- **Same code, different constants (no behaviour change)**: `ForgeUI_UIManager::PublishEvents` (identical after normalising), `GameCore::Achievements::IsAchievementUnlocked` and `ModdingLogger::~ModdingLogger` (only the vtable pointer differs).
- **Larger structs in the DX12 build** (member offsets shifted): `Civ6App` members after +0x5400 move by +0x20 and the `AppOptions.txt` handling by +0x20 (`OnLoadScreenClose`); `RenderGlobals::GraphicsOptions` fields from +0x48 on move by +0x18 (`CopyFromOptionSet`, `ReflectionsEnabled`: 0x60 -> 0x78); `Graphics::StartupParams` gets one more byte (+0xe) and a 4-byte field with value 0x10000 at +0x6c. These are layout changes only; the reason for the added members is not known (they may belong to the renderer).
- **New per-view flag in the water and terrain command building**: `WaterSystem::Context::BuildCommandStreams`, `BuildOverlayCommandStream`, `BuildReflectionMaskCommandStream` and `TerrainView::SubmitReflectionMask` (and one more parameter on the latter) read two flag bytes (+0x4e, +0x4f) of a view descriptor, set bit 0x200 in the command word and pass a 16-bit value from +0x50. Everything else in these functions is the same.
- `Civ6App::OnDebugConsoleInput` (the console help, 89% similar) differs by the 4 extra command words and a larger stack frame.
- **Rewritten renderer core**: `Renderer::Startup`, `Render`, `SetScreenMode`, `SetActiveDevices`, `EnumDisplayAdapters`, `InitFromShaderDef`, the `Create*Shader` / `Reload*Shader` family, `ConstantSet::Initialize`, `DeviceDatabase::GetDriverWorkAroundFlags`, the `Validation::PrintSupported*Formats` family and `CommandStream_D3D11` have no meaningful DX12 counterpart (similarity 0.02-0.47): the DX12 renderer is a different implementation behind the same interface.
Inferred: the 13 functions with no candidate (three `StrategicAudio::OnBarbarianClan*` handlers, `Civ6App::OverrideAppOptions`, several `Graphics::` functions) were probably merged by the linker (identical code folding): between the matched neighbours of the three 125-byte audio handlers only one 125-byte function remains in DX12. Not verified for the others.
Caveat on the matching: 73 of the 4,561 call-aligned matches and 478 exact ones land more than 0x30000 away from their DX11 address; some of these are real moves (identical thunks), but a few call-aligned ones are wrong (for example `Civ6App` 0x6ca80 -> 0x71b80 is out of order), so call-aligned matches should be treated as medium confidence.

## Vertex and index buffer creation in the DX12 exe (decompiled: DX12 0x944ee0, 0x943e90, 0x96cd40, 0x96a4e0, 0x940be0, 0x968a20, 0x975090; DX11 0x948cb0, 0x944fe0, 0x948d40, 0x945070, 0x940770)
Verified (decompiled text; RVAs = address - 0x140000000):
- Same wrapper structure as DX11. `CreateVB` (DX11 0x948cb0 -> DX12 0x944ee0) and `CreateIB` (0x944fe0 -> 0x943e90) take the same 7 parameters, allocate a 16-bit handle from a pool object (DX12 pool allocator 0x940be0 on the pool objects at 0xf2b50c0 (VB) and 0x6c72040 (IB); DX11 pool objects 0x2b91200 and 0x2b0a740) and call the real creation function (DX12 0x96cd40 VB, 0x96a4e0 IB; DX11 0x948d40, 0x945070). The pool allocator hands out handles below 0x2000, reuses freed ones and logs "ResourceList.AddResource(), attempting to add more than %d items" when full.
- DX11: the creation function fills a 0x30-byte record per handle and calls `ID3D11Device::CreateBuffer` (vtable slot 3, offset 0x18) writing the `ID3D11Buffer*` into the table at 0x2b99740 + handle*8. Usage 0 (static) requires initial data (logged otherwise), usage 1 = no data, usage 2 = dynamic (record gets 0x10000). Stride = table at 0x2d02c40 indexed by the format code.
- DX12: no `ID3D12Resource` per handle. The handle indexes two per-handle records: a 0x28-byte record (VB 0xf2bd4c0, IB 0x6c7a440) holding the buffer's GPU virtual addresses (two 8-byte entries, then a pointer to the backing heap object) plus stride (+0x18 VB), byte size (+0x1c) and format (+0x20 VB; for an IB the format is the DXGI code 0x2a R32_UINT or 0x39 R16_UINT, chosen by the format parameter being 0 = 16-bit), and a 0x70-byte record (VB 0xf30d600, IB 0x6cca580) holding the current allocation (+0x50), the previous one (+0x58), a pointer to the 0x28 record (+0x60), the aligned size (+0x68) and the flag byte (+0x6c). Stride table 0xf452580 (function 0x975090), same scheme as DX11.
- The data path is `FUN_140968a20` (0x968a20): a sub-allocator. The usage code (0..4) selects one of five pools (0x12957c0, 0x12959c0, 0x1295ac0, 0x12958c0, 0x1295cc0; dynamic usage 2 asks for 3x the size). A pool allocation has a backing buffer object (+0x48, with a CPU mapped base at +0x28 and a flags byte at +0x3c) and an offset (+0x5c). If a bit of the flags (bit 1) is clear the data is copied straight into the mapped memory (`FUN_1409903b0` = memcpy-like). If it is set, the data goes into a staging allocation and a copy is recorded for two targets (`FUN_140973bd0` called for entries 0 and 1). The GPU address stored per handle is `backing resource->GetGPUVirtualAddress()` (vtable slot 11, offset 0x58) + offset, for entries 0 and 1.
- Re-creation under an existing handle is supported by the code: if the 0x70 record already has an allocation (+0x50), the old one is released (`FUN_14096cf90`) and the new allocation, size and GPU addresses are installed, with the handle unchanged. In DX11 there is no such path (a new `ID3D11Buffer*` is written into the table slot).
Inferred:
- The two address entries are probably one per GPU node (the copy loop runs for 2); on a single GPU both would be the same or one unused. Not checked.
- Because the draw side uses GPU addresses stored in the record, patching entry 0/1 of the 0x28 record, or calling 0x96cd40 / 0x96a4e0 with an existing handle, would replace a buffer without changing the handle. Whether the draw code reads the VAs every frame or caches them was not looked at.
- Whether a static buffer's backing heap is CPU-visible (direct memcpy path) or default (staging path) depends on the pool; the flag in the pool object was not traced, so in-place updating of a given buffer is not established.
- Format codes 0x15 / 0x24 and the cell record layout were not compared.

## Pool heap types and the terrain cell record (tools/exe/dx12_cellscan.py; decompiled DX12 0x967dc0, 0x9682c0, 0x968040, 0x9678c0, 0x967b40, 0x96a750, 0x969ab0, 0x96dff0, 0x96ddd0)
Verified (decompiled code):
- The five pools of the buffer sub-allocator (0x968a20) differ in the heap they create. Allocations under 4 MB (0x400000) are carved out of 4 MB blocks (46 sub-allocations per page of 0x58 bytes); larger ones get a dedicated resource. Block and dedicated creation:
  - usage 0 and 1 (pools 0x12957c0, 0x12959c0, function 0x967dc0): `FUN_14096a750` = `ID3D12Device::CreateCommittedResource` (vtable offset 0xd8) with heap type DEFAULT (1), initial state 0xac3, one resource per GPU node (loop over the node count in 0x1444a94d8, stored at block+0x10 and +0x18), name "ResourceManager SmallBlock Buffer Resource (PRIVATE)". The block flag byte (+0x3c) gets bit 1 set, so data goes through a staging copy, never a direct memcpy.
  - usage 2 (pool 0x1295ac0, function 0x9682c0, 3x the size): `FUN_140969ab0` = CreateCommittedResource with heap type UPLOAD (2), name "...(UPLOAD)", persistently mapped (`Map`, slot 8), mapped pointer kept in the block; flag byte bit 0 set, so data is written straight to the mapped memory. The same function builds the staging pool (0x1295bc0, function 0x967b40, dedicated variant 0x96ddd0) used for the copies to DEFAULT buffers.
  - usage 3 (0x968040, block creator 0x96a600) and usage 4 (0x9678c0, dedicated only, 0x96dcc0) were not followed further.
- The terrain cell mesh creator `0xc62200` (DX12 `0xc70bf0`, exact match) calls `CreateVB` twice with usage 0 (`xor ecx,ecx`) and formats 0x15 (base mesh) and 0x24 (ID mesh), at the same code offsets (+0x11d, +0x19d) in both exes. So the cell VBs are usage 0, i.e. DEFAULT-heap (GPU-only) buffers in DX12: they cannot be rewritten by a CPU write to mapped memory. Changing them means replacing the allocation (re-create under the same handle, see above) or recording a GPU copy.
- Cell record: `GetRecord` computes (y*width + x)*0x3b0 + *(this+8) in both exes (byte-identical, 944 bytes), `GetCellStateData` adds *(this+0x18) to the same index. A scan for functions using the key record offsets (0x44, 0xc4..0xd8, 0x174..0x188, 0x18c, 0x398) or naming the Terrain_Cell buffers finds 104 functions in each exe; 102 are matched (90 exact, 10 call-aligned, 2 fuzzy) and every matched one uses an identical set of record offsets and names (the other 2 are renderer functions, not cell code). The record layout is therefore unchanged apart from what the access pattern shows; field meanings were not re-checked.
Inferred: that whether the draw code re-reads the stored GPU addresses each frame was not examined; item 6 (dirty bit -> re-bake) needs a runtime test; the matched cell functions are byte-equal or equal in offsets, which suggests the re-bake path is unchanged.
